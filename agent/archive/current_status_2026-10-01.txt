### Phase 4 limitations worth knowing

- **The live chat cannot show a completed answer yet, and that is correct.**
  The backend has no LLM provider adapters, so every `llm_response` stays
  `pending` forever. `verify_chat` asserts `pending` rather than faking a
  completion. Use `NEXT_PUBLIC_MOCK=1` to develop the completed/failed/metrics
  states.
- **The SSE stream is DB-polling, not token streaming** (1 s poll, 300 s cap,
  ending when all responses are final). A `response` event fires when a row
  changes, not per token — so the UI animates per completed model, not
  per-token text.
- **BACKEND DISCREPANCY found by `verify_chat`:** `.backend_agent/API.md` entry 38
  says `GET /chat/sessions/{id}/turns` returns "top-level turns" when no
  `parent_turn_id` is given, but the backend actually returns EVERY turn. Left
  unfiltered, a branch child would render twice — once in the main list and
  once nested under its parent. `useTurns` therefore filters to
  `parent_turn_id === null` client-side. Worth confirming with the backend team:
  either the docs or the implementation should change.
- **Long threads are not virtualized.** Item 36 says "virtualize if needed";
  `Markdown` and `ResponseCard` are memoized per block/token and long content
  is fine up to a few hundred turns, but a thread with thousands of turns will
  eventually need windowing. Left out deliberately: it is real complexity that
  is not yet justified, and it is the obvious follow-up.

  this explicitly rather than hiding the control.
- Google sign-in is wired end to end but untestable locally: `GOOGLE_CLIENT_ID`
  is unset upstream, so the BFF answers 503 / error.upstream.

- `npm run verify:bff` needs a running `npm run start -- -p 3100`. It drives
  the cookie jar explicitly because the cookies are `Secure` in production and
  would otherwise be dropped by a plain-HTTP client.

## Locked decisions (details in project_structure_graph.txt)

- Next.js 16 App Router (Turbopack default) + React 19 + TypeScript 6 strict.
- Single-file theming: ALL colors belong in `src/styles/theme.css`; only
  `global-error.tsx` deviates, and it is documented in the theme file header.
- Dark mode is class-based (`.dark` on `<html>`), driven by next-themes with
  `defaultTheme="system"`. Tailwind's `dark:` variant is re-pointed to the
  class in `globals.css`.
- Route groups: `(auth)` = shell-free auth pages, `(app)` = sidebar/topbar
  shell. `/` redirects into `/dashboard`.
- Microservice boundaries: BFF gateway (src/app/api/**, thin handlers) +
  feature modules (src/modules/*) + server-only helpers (src/server/**). Only
  `src/server` knows the upstream host and the tokens.
- Session = two httpOnly cookies (`at`, `rt`). No token ever reaches browser JS.
- The route guard is `src/proxy.ts`, not `middleware.ts` — Next 16.3.8 renamed
  the convention and warns at build time on the old filename.
- Security headers are applied in next.config.ts and the cookie session is live;
  the CSP (nonce/headers() strategy) still lands in the phase 7 security pass.

## Environment notes for the next session

- The terminal harness in this environment KILLS long-running foreground
  processes and reports "Command completion could not be observed". Run long
  commands detached and poll the log file, e.g.
  `Start-Process cmd -ArgumentList '/c','npm run build > out.log 2>&1 & echo EXIT=%ERRORLEVEL% >> out.log' -WindowStyle Hidden`
  then read `out.log`. Budget 2-5 minutes for build/lint on this slow disk.
- The dev server on this machine also logs "Slow filesystem detected
  (925ms)"; first-compile of a route takes ~20s. That is environmental, not a
  code problem.
- The backend must be running for both smoke suites:
  `cd ../backend && venv\Scripts\python.exe -m uvicorn main:app --port 8000`
- `npm run verify:bff` also needs the frontend built and served:
  `npm run build && npm run start -- -p 3100`.
- Cookies are `Secure` under `next start` (production), so a plain-HTTP test
  client drops them. That is why `verify_bff_gateway.mjs` drives an explicit
  cookie jar rather than relying on a cookie-aware fetch.
- **Editor caveat learned this session:** `insert_line: N` on a long file
  inserts *before* line N but the tool's reported line can drift; twice a
  multi-chunk insert left an orphaned block at EOF. Always `node --check`
  scripts, or re-read the boundary, after appending in chunks.
